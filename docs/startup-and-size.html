Startup time and size of the clients

How long the web app and the native app (native/, V on sokol) take to start on a phone, and how big each one is. Measured to weigh the web app against the native client and the other ways to ship the app.

Measured 2026-10-31; Chrome against Chrome Beta on 2026-11-01. Rerun the startup numbers with tasks/measure-startup.sh.

Setup

  • Phone: Moto G7 (2019, Snapdragon 632, arm64), Android 10, Chrome 156. Chrome had about 90 tabs open; they don't slow the web app's start (see Chrome against Chrome Beta).
  • Web app: soccer.jnyman.com, installed from Chrome (a WebAPK), opening on /web/teams with real data.
  • Native app: com.jnyman.soccer, a -prod build from V 0.5.2.
  • Desktop: Linux x86_64.

What it shows

  • Chrome is the cost, not the app. Starting Chrome takes 1.9–2.9 s before the page is even requested. The service worker then boots, opens IndexedDB and renders /web/teams in under 0.11 s, so trimming the app's code would hardly show.
  • Cold starts vary between sessions. They took 3.1–3.2 s in one set and 2.1–2.2 s in the next, likely from what Chrome had loaded or the phone's state. The app's own share stayed the same.
  • With Chrome already running, the web app opens in about 1.1–1.3 s.
  • Chrome's open tabs don't matter. A copy installed from Chrome Beta, which has no tabs, starts no faster (below).
  • The native app draws its first frame in about 0.2–0.3 s: about 5× faster than the web app with Chrome running, and 9–14× faster than from cold.
  • Capacitor (wrapping the web app for the app stores) starts its own WebView and can't reuse a running Chrome, so expect it between the two web cases. On iOS it also needs App-Bound Domains for the service worker, which this app is built around. Not measured.

Chrome against Chrome Beta

Chrome had about 90 tabs open, so would a browser kept just for the app start faster? The app was installed a second time from Chrome Beta 158, a separate browser with its own profile and no tabs, and both copies were timed back to back (Chrome 156). Median of 5 runs each, tap → loaded:

Case Chrome (90 tabs) Chrome Beta (no tabs)
Browser not running 2.20 s 2.22 s
Browser already running 1.14 s 1.26 s
Tap → page requested, not running 1.99 s 1.98 s
Service worker, not running 89 ms 122 ms

Every run, tap → loaded. Chrome, not running: 2.78, 2.16, 2.22, 2.18, 2.20 s; running: 1.10, 1.14, 1.13, 1.15, 1.14 s. Chrome Beta, not running: 3.00, 2.30, 2.20, 2.21, 2.22 s; running: 1.23, 1.26, 1.27, 1.24, 1.27 s. The first cold run was slower for both. The native app, timed in the same session, took 0.21 s.

  • From cold they tie. Nearly all of it is the browser starting (about 2.0 s before the page is requested), and that is the cost of starting Chromium on this phone, not of the tabs. Chrome doesn't reload its tabs when it starts only for an installed web app.
  • With the browser running, Chrome is about 0.1 s faster. A fresh profile gains nothing.
  • So keep the app in Chrome. A separate browser only for the app adds a second copy of its data (each browser has its own IndexedDB and login) without starting any faster.

How it is measured

  • Web app: the browsers and the app are force-stopped, then the app is opened from its launcher, with the phone's clock read just before. Each installed copy is timed in the browser it was installed from, read from its manifest.
  • Reading the timing: the page's navigation timing, read through Chrome's remote debugging, gives when the page was requested (performance.timeOrigin), how long the service worker took to answer (responseStart − workerStart), and when the page finished loading (loadEventEnd).
  • No paint timings: Chrome loads the page behind its splash screen, so "loaded" is the closest to when it appears.
  • "Chrome already running": the browser is opened first and left 15 s to settle.
  • Native app: am start -W, the time to its first frame.

Every page's routes in the page

Since 2026-11-02 every page runs the service worker's routes itself (src/web/js/routes.bundle.ts, loaded once the page is idle): forms and links that open in the htmz iframe, and the next page when moving between pages (htmz-nav's window.htmzFetch). It runs the worker's own router and middleware on the same IndexedDB, so the answer is the same; what calls the server (sync, the account, sharing, a published schedule) stays in the worker. Test data, dev build, the same phone, medians in ms:

Measure Before (2 runs) After (4 runs)
A stats tab (a link into the htmz iframe; 15 taps a run) 105–107 ms 41–46 ms
Moving between pages (6 pages, click to drawn) 49–73 ms 37–65 ms
Match taps, all (already in the page before) 78–84 ms 86–90 ms
Page load, navigation to first paint 244–344 ms 216–308 ms
Load to the routes running in the page — 149–201 ms

Match taps aren't slower, though the table suggests 5–10 ms: run back to back, the two measured 84 ms (before) and 86 ms (after), and a Chrome trace of 28 taps each found the same work on the main thread (tap to merged 77.3 against 76.0 ms, merged to the next frame 27.3 against 27.1 ms). The earlier gap came from when each was run: the runs before were after a rest, those after back to back. Moving between pages gains least on Games and Stats, the same as before. The extra code (44 KB, plus the page's own the first time it's used) loads after the load event, so it doesn't hold up the first paint.

What running in the page changes

  • Taps: about 140–180 ms through the service worker. Some 80–130 ms of that is the round trip: starting the form's request, the service worker's work, and loading its response as a document. Running the same handlers and templates in the page, in plain JS, skips it: 82–85 ms median in two runs (measured, above), under the ~100 ms where a tap feels instant. What is left is mostly the handler and re-rendering the whole view; a framework updating only what changed could take that further, towards the 50–60 ms first estimated.
  • Pages: about 125–245 ms as a new document, of which the service worker is only 13–33 ms. The rest is the browser loading the document: parsing it, its CSS and scripts, layout. Links in the app now fetch the next page (the service worker still renders it) and morph it into the current one, with history.pushState so the address, reload, back and forward behave as before (@jon49/web/htmz-nav.js): 47–80 ms from the click to the new page drawn, against 214–253 ms for the same pages loaded as documents (test data, 2026-11-01). Pages that need other stylesheets or scripts (Settings, Share, the match play view) still load as documents.
  • Startup wouldn't change: Chrome's start dominates (above).

Size

Web app

The production build (npm run build, as the publish script ships it):

Web app Size
App files (38 files, uncompressed) 270 KB
Download (compressed, as served) 106 KB
  • By type, uncompressed: JavaScript 190 KB (25 files), CSS 48 KB, HTML 8 KB, icons 23 KB.
  • Biggest files: the service worker's shared code (shared.global.js, 33 KB), the match page (31 KB), the CSS (base.css, 31 KB), and the page script (app.bundle.js, 19 KB).
  • It used to be 290 KB (107 KB to download): base.css shipped twice, hashed and unhashed, for the pages outside the service worker. Each page now links it itself, before app.css, instead of app.css importing it (see "Hashed asset names" in CLAUDE.md).
  • The build also ships pre-compressed .gz copies, which aren't counted.
  • Why so small: it is about 20× smaller than the trimmed APK because it relies on Chrome, which is already on the phone. The cost is Chrome's startup (above), not the download.

The small, fast native client comes with gaps; these took work in this project or are still open:

  • Desktop: sokol sets no window class or app id and ignores the keymap. Both are fixed by reaching into sokol's private state.
  • Android: sokol drops key events, can't show the keyboard and quits on Back, all fixed with our own Java activity. A hardware keyboard and copy and paste are still missing.
  • iOS: blocked inside V's net module.
  • Everywhere: no accessibility (screen readers get nothing) and no input method for languages like Chinese or Japanese.
